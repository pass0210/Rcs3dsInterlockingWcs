WCS ↔ RCS · API Interface Specification

WCS ↔ RCS Interface Specification REST / JSON API. WCS integrates with RCS in two operating modes — Part I · B2C (real-time 3D-sorter integration: IF-05/08/09/10, WCS decides the destination and pushes status) and Part II · B2B (batch test-data method: five /api/v1/works/* endpoints, no 3DS handshake, no destination decision). The two modes share no endpoints. Endpoint/auth/timing values marked as examples are open to discussion, but the B2B wire contract (fields, types, failure messages) is fixed.

◎ Two Operating Modes (B2C real-time / B2B batch)

WCS integrates with RCS in two operating modes. Because the endpoint sets are entirely separate, you only need to read the part for your mode.

In this document, B2C / B2B are labels for the integration method (wire contract). Which one to read — if you tilt to a live 3D sorter in real time, read B2C (Part I · §1–§8); if you consume pre-registered batch data, read B2B (Part II). B2B is also a production path — despite the name "batch test-data method," it is not test-only and is used in real operation.

Part I · B2C
Real-time 3D-sorter integration
Per-piece processing immediately on the induction scan. RCS calls destination query, arrival report and deposit report (IF-05/09/10); WCS pushes destination status (IF-08) on every change. WCS performs the destination decision and the 3DS Modbus handshake internally. (§1–§8 below)

1 Overview & Roles

WCS holds the orders and destination assignments. RCS controls the AGVs/robots. At an induction (infeed) point a robot receives the item(s) onto its tray, asks WCS for the destination, drives to that destination (a chute), and tilts the entire tray quantity at once (full tilt — no partial deposit).

  • Two directions. IF-05, IF-09 and IF-10 are RCS→WCS requests (WCS responds). IF-08 is a WCS→RCS push — WCS notifies RCS of each destination's status (a plain chute or a 3D-sorter chute) whenever it changes.
  • Arrival notification. When the AGV reaches the chute, RCS sends an arrival report (IF-09). RCS deposits once the destination is ready in the IF-08 status. (How WCS prepares the 3D sorter internally is not RCS's concern.)
  • Real-time, continuous. No batch start/stop. Each item is handled as it arrives at induction.
  • Destination = chuteNo. The destination is addressed by a chute number.
  • RCS decides deposit locally. Instead of polling for permission, RCS keeps the latest destination status (from IF-08 pushes) and deposits when that destination is ready — otherwise it waits for the next update.

5 API Definitions

IF-05 Destination Query

Proposed: POST /api/v1/destination-query. Called once at the induction scan. WCS records the piece (tracking starts; the record is kept even if the result is NG) and decides the destination and quantity.

RequestResponse
pId, agvNo, barcode, inductionNo, qty, timeStampresult (OK / NG), chuteNo (present when OK; null on NG)
// request
{ "pId": 1024, "agvNo": 7, "barcode": "8801234567890",
  "inductionNo": 2, "qty": 3, "timeStamp": "2026-06-08 14:30:00" }

// response — OK
{ "result": "OK", "chuteNo": 15 }

// response — NG (no destination right now)
{ "result": "NG", "chuteNo": null }

On OK the RCS drives the AGV to chuteNo. On NG the AGV waits and the call is retried later (see Reason Codes).

IF-08 Destination Status (push · WCS → RCS)

Proposed: POST {RCS base}/api/v1/destination-status — endpoint hosted by RCS, WCS is the caller. WCS pushes a destination's status whenever it changes (state-change driven, not periodic). A destination is a plain chute or a 3D-sorter chute — RCS treats them the same. RCS keeps the latest status per chuteNo and, when its AGV is at that chute, deposits as soon as it is ready — otherwise it waits for the next push.

Request (WCS → RCS)Response (RCS → WCS)
chuteNo, ready, timeStampresult (OK)
// request (WCS → RCS · on status change)
{ "chuteNo": 15, "ready": true, "timeStamp": "2026-06-22 14:30:00" }

// response (RCS → WCS)
{ "result": "OK" }

ready=true = the destination can receive now (OK); ready=false = it cannot (NG). A plain chute is ready=false when full or paused (which WCS manages). A 3D-sorter chute's ready=false is for operating-status reasons only — sorting / moving / not aligned / offline. The sorter's cell full / paused do NOT make push ready false (even when full/paused, if the operating status is OK then ready=true); those two are blocked at IF-05 dispatch. RCS deposits when ready=true; otherwise it holds and waits for the next push.

IF-09 Arrival Report

Proposed: POST /api/v1/arrival-report. Sent once when the AGV reaches the destination chute, before depositing. WCS records the arrival and prepares the destination to receive. RCS then waits for that destination to turn ready in the IF-08 status push and deposits.

RequestResponse
pId, chuteNo, agvNo, timeStampresult (OK)
// request
{ "pId": 1024, "chuteNo": 15, "agvNo": 7, "timeStamp": "2026-06-22 14:30:00" }

// response
{ "result": "OK" }

For a chute-only destination (no 3D sorter) WCS simply records the arrival. For a 3D-sorter chute WCS prepares it to receive (internal — no floor info is exchanged with RCS).

IF-10 Deposit Report

Proposed: POST /api/v1/deposit-report. Sent after the tilt. The full qty is tilted at once.

RequestResponse
pId, barcode, chuteNo, agvNoresult (OK)
// request

// response
{ "result": "OK" }

6 Reason Codes

IF-05 reasons are internal to WCS — recorded in the WCS piece log and not returned to RCS (RCS sees only result). IF-08 is no longer a permission query but a status push; the table below shows how RCS interprets the pushed destination status.

IF-05 — Destination Query

WCS reason (internal)RCS seesRCS action
NORMALOKMove AGV to chuteNo
BUSY (sorting / moving)OKStill move to chuteNo — the sorter is busy now but frees up shortly; deposit when it turns ready in the IF-08 status
FULL / PAUSED (by destination type)NG wait / OKDepends on the destination type. Plain chute: even when full/paused, IF-05 returns OK (send and wait — readiness is delivered separately by the IF-08 push). 3D sorter: PAUSED → NG (blocked without exception); if it cannot receive by cell (SorterCanAcceptBarcode) → NG (FULL); OFFLINE is not considered in IF-05 (if a cell exists, OK even when offline — wait for push ready after arrival). That is, the IF-05 decision is by paused + cell room, not by ready (operating status)
OVERNG waitHold AGV (full quantity does not fit one destination yet)
COMPLETED / NO_DEST / OFFLINENG waitHold AGV — no destination (OFFLINE = destination unreachable; alternate / hold)
Footnote — the two OFFLINEs in the table above are different situations. The OFFLINE in the FULL / PAUSED row is the sorter's operating status (poll timeout / socket drop); IF-05 dispatch does not consider it, so it is OK when a cell exists (wait for push ready after arrival). The OFFLINE in the COMPLETED / NO_DEST / OFFLINE row is when the destination itself cannot be determined (connection lost / no destination), which is NG.

7 End-to-End Flow

① Destination Query→ ② Arrival report (IF-09)→ ③ Wait for ready (IF-08 status push)→ ④ Deposit Report
  1. ① Destination Query — At the scan, RCS calls IF-05. On OK, RCS drives the AGV to chuteNo; on NG, the AGV waits.
  2. ② Arrival report (IF-09) — On reaching the chute, RCS calls IF-09. WCS records the arrival and prepares the sorter to receive.
  3. ③ Ready (IF-08 push) — RCS keeps receiving destination status from WCS. It deposits as soon as that chute is ready=true; otherwise it waits for the next push.
  4. ④ Deposit Report — RCS tilts the full qty at the destination and calls IF-10 to report it.

Part II · B2B
Batch test-data method
Batch-level input / classification / results built on pre-registered test data (bizDay + batch + barcode). It consists of five REST endpoints only; there is no 3DS Modbus handshake, no destination decision, no IF-08 status push, and no floor concept.

B1 Overview & Role

The B2B mode exchanges batch-level input, classification and results based on pre-registered test data (bizDay + batch + barcode). The destination (chuteNo) is already assigned in the batch data, so WCS does not decide it.

  • Batch-based. The unit of processing is pre-registered data grouped by bizDay/batch — not a real-time piece stream (B2C).
  • No destination decision. chuteNo is already in the batch data, so WCS does not compute a destination.
  • One-way calls. All five endpoints are RCS → WCS (unprocessed is GET, the rest POST). There is no WCS → RCS status push (IF-08).
  • Branch on status. The client decides the processing outcome by the response status (S/F) field, not the HTTP status code.
No 3DS integration. B2B has no destination decision, IF-08 status push, or 3D-sorter handshake — it runs on the five REST APIs alone. (PLC registers, Modbus handshake and floor alignment are outside the RCS interface scope; see Part I · B2C and the master spec §07·§08.)

chuteNo normalization. The server normalizes chuteNo to a 3-digit zero-pad on every endpoint (e.g. "3" → "003"). Classification's chute match ("Chute mismatch") compares the padded value, so "1" and "001" are treated as the same chute.

① Query Unprocessed Batch — GET /api/v1/works/unprocessed?bizDay=

Queries the list of unprocessed data. The response is a raw array, not ApiResponse, and when there is no data it returns an empty array [] + 200 (not a failure).

Side effects. It updates each queried row's ReceiveTime to the server time ("taken" marking). ⚠ It is a GET but not idempotent — do not blindly retry even if the response fails to arrive. Each call consumes the rows it returns (ReceiveTime marking), so retrying fetches the next set of rows rather than the previous ones, which can lose data.
※ When there are 0 unprocessed rows, it returns an empty array [] (not a failure).

B6 Failure Responses & Reasons (status:"F")

On failure, every endpoint returns {"status":"F","message":"..."}. The client must always branch on the status field, not the HTTP status code. The message strings below are the exact strings the server returns (braces {...} are runtime-substituted values).

status:"F" (server response) differs from the request-body status:"NG". "F" means the server rejected/failed the call; "NG" is a bad item that is received normally and logged — the server accepts it and returns "S".

B7 Flow (Golden Path)

RCS calls in the following order. Each step's purpose and its action on failure (especially whether a retry is safe) are below.

① unprocessed query→ ② input→ ③ classification→ ④ box close (optional)→ ⑤ results
StepPurposeAction on failure
① unprocessedObtain batch data to process + mark queried rows as "taken"Do not retry (non-idempotent — each call consumes rows). If the response is lost, re-querying fetches different rows, so use operator confirmation / re-sync. An empty array is not a failure.
② inputRecord input (grouped by qty)On status:"F" the whole call is rejected (no partial) — check the cause via message. On "Not enough unprocessed rows," re-query ① to re-check availability, then resend. If no response arrived (timeout), there is a double-consume risk, so resend only after verifying whether it was applied.
③ classificationRecord classification result (grouped by qty)Chute mismatch / already classified / insufficient rows will fail identically on retry unless the data is corrected. Fix the cause, then resend. The timeout-resend caution is the same as ②.
④ box (optional)Record a box-level closingResending the same (bizDay,batch,boxNo) is rejected by the duplicate key — it is already stored, so no retry is needed.
⑤ resultsSend all results in bulk (top-level array)If even one barcode is unregistered, the whole request is rejected (no partial INSERT). After fixing the barcode, resending the whole request is safe.

B8 Timing & Retry

ItemValueNote
Rate limit300 requests/min per IPOver the limit returns 429 — see the retry rules below
  • Do not retry unprocessed (GET) — it is non-idempotent and each call consumes rows. Even if you did not receive the response, re-querying fetches the next set of rows and loses data, so on timeout handle it via operator confirmation / re-sync.
  • Retrying a POST is safe only when it is certain the server did not process it — the connection never reached the server, or you received a definite status:"F" and fixed the cause. Blindly resending an input/classification that timed out without a response can double-consume the unprocessed pool, so verify whether it was applied (via a query or a results comparison) before resending. Resending box is safe because the duplicate key is rejected.
  • Retry 429 with exponential backoff — it occurs above 300 requests/min (per IP), so do not retry immediately; wait between attempts.
  • 500 leaves the outcome uncertain, so follow the POST retry rule above (verify application first).
