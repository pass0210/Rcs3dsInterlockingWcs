WCS ↔ RCS · API Interface Specification

WCS ↔ RCS Interface Specification REST / JSON API. RCS calls WCS for destination, arrival & report (IF-05 / IF-09 / IF-10); WCS pushes destination status (IF-08) to RCS on every change. Real-time, per induction (no batch). This document specifies the WCS ↔ RCS interface; endpoints, auth and timing values are examples and open to discussion.

1 Overview & Roles

WCS holds the orders and destination assignments. RCS controls the AGVs/robots. At an induction (infeed) point a robot receives the item(s) onto its tray, asks WCS for the destination, drives to that destination (a chute), and tilts the entire tray quantity at once (full tilt — no partial deposit).

  • Two directions. IF-05, IF-09 and IF-10 are RCS→WCS requests (WCS responds). IF-08 is a WCS→RCS push — WCS notifies RCS of each destination's status (a plain chute or a 3D-sorter chute) whenever it changes.
  • Arrival notification. When the AGV reaches the chute, RCS sends an arrival report (IF-09). RCS deposits once the destination is ready in the IF-08 status. (How WCS prepares the 3D sorter internally is not RCS's concern.)
  • Real-time, continuous. No batch start/stop. Each item is handled as it arrives at induction.
  • Destination = chuteNo. The destination is addressed by a chute number.
  • RCS decides deposit locally. Instead of polling for permission, RCS keeps the latest destination status (from IF-08 pushes) and deposits when that destination is ready — otherwise it waits for the next update.

5 API Definitions

IF-05 Destination Query

Proposed: POST /api/v1/destination-query. Called once at the induction scan. WCS records the piece (tracking starts; the record is kept even if the result is NG) and decides the destination and quantity.

RequestResponse
pId, agvNo, barcode, inductionNo, qty, timeStampresult (OK / NG), chuteNo (present when OK; null on NG)
// request
{ "pId": 1024, "agvNo": 7, "barcode": "8801234567890",
  "inductionNo": 2, "qty": 3, "timeStamp": "2026-06-08 14:30:00" }

// response — OK
{ "result": "OK", "chuteNo": 15 }

// response — NG (no destination right now)
{ "result": "NG", "chuteNo": null }

On OK the RCS drives the AGV to chuteNo. On NG the AGV waits and the call is retried later (see Reason Codes).

IF-08 Destination Status (push · WCS → RCS)

Proposed: POST {RCS base}/api/v1/destination-status — endpoint hosted by RCS, WCS is the caller. WCS pushes a destination's status whenever it changes (state-change driven, not periodic). A destination is a plain chute or a 3D-sorter chute — RCS treats them the same. RCS keeps the latest status per chuteNo and, when its AGV is at that chute, deposits as soon as it is ready — otherwise it waits for the next push.

Request (WCS → RCS)Response (RCS → WCS)
chuteNo, ready, timeStampresult (OK)
// request (WCS → RCS · on status change)
{ "chuteNo": 15, "ready": true, "timeStamp": "2026-06-22 14:30:00" }

// response (RCS → WCS)
{ "result": "OK" }

ready=true = the destination can receive now (OK); ready=false = it cannot (NG). For a plain chute that means full or paused (which WCS manages); for a 3D-sorter chute also busy / offline / not aligned. WCS folds all of it into one flag, so RCS acts on a single chute-level ready and won't tilt into a full or paused chute. RCS deposits when ready=true; otherwise it holds and waits for the next push.

IF-09 Arrival Report

Proposed: POST /api/v1/arrival-report. Sent once when the AGV reaches the destination chute, before depositing. WCS records the arrival and prepares the destination to receive. RCS then waits for that destination to turn ready in the IF-08 status push and deposits.

RequestResponse
pId, chuteNo, agvNo, timeStampresult (OK)
// request
{ "pId": 1024, "chuteNo": 15, "agvNo": 7, "timeStamp": "2026-06-22 14:30:00" }

// response
{ "result": "OK" }

For a chute-only destination (no 3D sorter) WCS simply records the arrival. For a 3D-sorter chute WCS prepares it to receive (internal — no floor info is exchanged with RCS).

IF-10 Deposit Report

Proposed: POST /api/v1/deposit-report. Sent after the tilt. The full qty is tilted at once.

RequestResponse
pId, barcode, chuteNo, agvNoresult (OK)
// request
{ "pId": 1024, "barcode": "8801234567890", "chuteNo": 15, "agvNo": 7 }

// response
{ "result": "OK" }

6 Reason Codes

IF-05 reasons are internal to WCS — recorded in the WCS piece log and not returned to RCS (RCS sees only result). IF-08 is no longer a permission query but a status push; the table below shows how RCS interprets the pushed destination status.

IF-05 — Destination Query

WCS reason (internal)RCS seesRCS action
NORMALOKMove AGV to chuteNo
BUSY (sorting / moving)OKStill move to chuteNo — the sorter is busy now but frees up shortly; deposit when it turns ready in the IF-08 status
FULL / PAUSEDNG waitHold AGV — destination cannot receive (long block). With no IF-08 permission query, WCS does not hand out a full/paused destination
OVERNG waitHold AGV (full quantity does not fit one destination yet)
COMPLETED / NO_DEST / OFFLINENG waitHold AGV — no destination (OFFLINE = destination unreachable; alternate / hold)

IF-08 — Destination Status (how RCS interprets the push)

Pushed statusRCS action
ready=true (OK)deposit Proceed to tilt
ready=false (NG)wait Destination can't receive now (full / paused; for a sorter also busy / offline) — deposit on a later push when it turns ready

7 End-to-End Flow

① Destination Query→ ② Arrival report (IF-09)→ ③ Wait for ready (IF-08 status push)→ ④ Deposit Report
  1. ① Destination Query — At the scan, RCS calls IF-05. On OK, RCS drives the AGV to chuteNo; on NG, the AGV waits.
  2. ② Arrival report (IF-09) — On reaching the chute, RCS calls IF-09. WCS records the arrival and prepares the sorter to receive.
  3. ③ Ready (IF-08 push) — RCS keeps receiving destination status from WCS. It deposits as soon as that chute is ready=true; otherwise it waits for the next push.
  4. ④ Deposit Report — RCS tilts the full qty at the destination and calls IF-10 to report it.
