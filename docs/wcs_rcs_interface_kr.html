WCS ↔ RCS · API 인터페이스 — RCS 검토용

WCS ↔ RCS 인터페이스 정의서 REST / JSON API. RCS가 클라이언트(WCS를 호출), WCS는 응답만 한다. 실시간·투입 단위(배치 없음). 본 문서는 RCS 측 구현 가능 여부를 검토받기 위한 제안 — 엔드포인트·인증·시간값은 예시이며 협의 가능.

1 개요 & 역할

WCS가 오더와 목적지 배정을 보유한다. RCS는 AGV/로봇을 제어한다. 인덕션(투입구)에서 로봇이 트레이에 상품을 받아 WCS에 목적지를 조회하고, 그 목적지(슈트)로 이동해 트레이 수량 전량을 한 번에 틸트한다(부분 투입 없음).

  • RCS가 호출, WCS가 응답. 세 인터페이스 모두 RCS → WCS HTTP 요청이며 WCS가 JSON으로 응답한다. 현재 설계에 WCS→RCS 푸시는 없다.
  • 실시간·연속. 배치(차수) 시작/종료 없음. 상품이 인덕션에 들어오는 즉시 처리.
  • 목적지 = chuteNo. 목적지는 슈트 번호로 지정한다.
  • 투입 가부(IF-08)의 내부 판정은 WCS가 한다. RCS는 allowed / reason 결과만 보면 된다.

5 API 정의

IF-05 목적지 조회

제안: POST /api/v1/destination-query. 인덕션 스캔 시 1회 호출. WCS가 피스를 기록하고(추적 시작 — 결과가 NG여도 기록은 남음) 목적지·수량을 판정한다.

요청(req)응답(res)
pId, agvNo, barcode, inductionNo, qty, timeStampresult (OK / NG), reason, chuteNo (OK일 때 포함)
// 요청
{ "pId": 1024, "agvNo": 7, "barcode": "8801234567890",
  "inductionNo": 2, "qty": 3, "timeStamp": "2026-06-08 14:30:00" }

// 응답 — OK
{ "result": "OK", "reason": "NORMAL", "chuteNo": 15 }

// 응답 — NG (지금 보낼 목적지 없음)
{ "result": "NG", "reason": "OVER", "chuteNo": null }

OK이면 RCS가 AGV를 chuteNo로 이동시킨다. NG이면 AGV는 대기하고 이후 다시 호출한다(사유 코드 참조).

IF-08 투입 가부

제안: POST /api/v1/deposit-permission. AGV가 목적지에 도착해 투입 직전에 호출. WCS가 내부에서 가부를 판정하며, RCS는 결과만 받아 allowed=true가 될 때까지 500ms 간격(협의 가능)으로 폴링한다.

요청(req)응답(res)
pId, chuteNo, agvNoallowed (true / false), reason
// 요청
{ "pId": 1024, "chuteNo": 15, "agvNo": 7 }

// 응답 — 아직 AGV 층이 아님 (WCS가 처리 중)
{ "allowed": false, "reason": "WRONG_FLOOR" }

// 응답 — 투입 가능
{ "allowed": true, "reason": "READY" }

IF-10 투입 보고

제안: POST /api/v1/deposit-report. 틸트 후 전송. qty 전량을 한 번에 틸트한다.

요청(req)응답(res)
pId, barcode, chuteNo, agvNoresult (OK)
// 요청
{ "pId": 1024, "barcode": "8801234567890", "chuteNo": 15, "agvNo": 7 }

// 응답
{ "result": "OK" }

6 사유 코드

IF-05 — 목적지 조회

reasonresultRCS 동작
NORMALOKAGV를 chuteNo로 이동
BUSY / FULL / PAUSEDOK그래도 chuteNo로 이동(일시적 막힘 — 도착 후 IF-08에서 실제 가부 재확인)
OVERNG 대기AGV 대기(전량이 한 목적지에 아직 안 들어감)
COMPLETED / NO_DEST / OFFLINENG 대기AGV 대기 — 보낼 목적지 없음(OFFLINE = 목적지 연결 끊김; 대체 / 보류)

IF-08 — 투입 가부

allowedreasonRCS 동작
trueREADY투입(틸트 진행)
falseWRONG_FLOOR목적지가 아직 AGV 층에 정렬되지 않음 — WCS가 처리 중. 500ms(협의 가능) 뒤 재호출
falseBUSY / FULL / PAUSED / OFFLINE지금 받을 수 없음. 앞에서 대기하며 500ms(협의 가능) 간격으로 true 될 때까지 재호출

7 전체 플로우

① 목적지 조회→ ② 투입 가부 (500ms 폴링·협의 가능)→ ③ 투입 보고
  1. ① 목적지 조회 — 스캔 시 RCS가 IF-05 호출. OK면 AGV를 chuteNo로 이동, NG면 AGV 대기.
  2. ② 투입 가부 — 목적지에서 RCS가 IF-08을 allowed=true가 될 때까지 500ms(협의 가능) 간격으로 반복. WRONG_FLOOR / BUSY / FULL / PAUSED / OFFLINE은 “대기 후 재시도”.
  3. ③ 투입 보고 — RCS가 목적지에서 qty 전량을 틸트하고 IF-10으로 보고.

9 RCS 확인 사항 (구현 가능 여부)

아래 항목을 RCS 측에서 구현 가능한지 검토·회신 부탁드립니다. 위에서 “제안/미정”으로 표기된 부분은 RCS 의견을 반영할 수 있습니다.

  1. HTTP 클라이언트. RCS가 클라이언트로서 WCS REST/JSON 엔드포인트를 투입마다 실시간으로 호출할 수 있습니까(배치 아님)?
  2. 피스 ID(pId). RCS가 pId를 1–30000 범위로 부여·전송할 수 있습니까? 가능하다면 30000에 도달하면 1로 순환할지, 매일 1로 초기화할지 정책을 알려주세요.
  3. 인덕션 데이터. 스캔 시 RCS가 agvNo, barcode, inductionNo, qty를 제공할 수 있습니까?
  4. IF-05 처리. OK면 AGV를 chuteNo로 이동, NG면 AGV 대기 후 재시도 — 가능합니까?
  5. IF-08 폴링. RCS가 투입 가부를 allowed=true까지 500ms(협의 가능) 간격으로 폴링하고, WRONG_FLOOR / BUSY / FULL / PAUSED / OFFLINE을 “목적지 앞에서 대기·재시도”로 처리할 수 있습니까?
  6. IF-10 보고. 틸트(투입) 후 투입 보고(IF-10)를 전송할 수 있습니까?
  7. 접속 & 인증. 어떤 Base URL / IP / 포트를 사용하며, 어떤 인증을 지원합니까(없음 / API 키 / mTLS 등)?
