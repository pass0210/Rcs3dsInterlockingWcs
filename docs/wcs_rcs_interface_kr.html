WCS ↔ RCS · API 인터페이스 정의서

WCS ↔ RCS 인터페이스 정의서 REST / JSON API. WCS는 두 가지 운영 방식으로 RCS와 연동한다 — Part I · B2C(실시간 3D 소터 연동: IF-05/08/09/10, WCS 목적지 판정·상태 푸시)와 Part II · B2B(배치 테스트데이터 방식: /api/v1/works/* 5종, 3DS 핸드셰이크·목적지 판정 없음). 두 방식은 공유 엔드포인트가 없다. 엔드포인트·인증·시간값 중 예시 표기는 협의 가능하나, B2B 와이어 계약(필드·타입·실패 message)은 확정값이다.

◎ 2가지 운영 방식 (B2C 실시간 / B2B 배치)

WCS는 두 가지 운영 방식으로 RCS와 연동한다. 엔드포인트 집합이 완전히 분리되어 있으므로, 담당하는 방식의 파트만 읽으면 된다.

B2C / B2B는 이 문서에서 연동 방식(통신 계약)을 가리키는 라벨이다. 어느 쪽을 읽을지 — 라이브 3D 소터에 실시간으로 틸트하면 B2C(Part I · §1~§8), 사전 등록된 배치 데이터를 소비하면 B2B(Part II)를 읽는다. B2B도 정식 운영 경로다 — "배치 테스트데이터 방식"이라는 이름이지만 테스트 전용이 아니라 실제 운영에 사용된다.

Part I · B2C
실시간 3D 소터 연동
인덕션 스캔 즉시 피스 단위로 처리. RCS가 목적지 조회·도착 보고·투입 보고(IF-05/09/10)를 호출하고, WCS가 목적지 상태(IF-08)를 변경 시마다 RCS로 푸시한다. 목적지 판정과 3DS Modbus 핸드셰이크는 WCS 내부에서 수행한다. (아래 §1~§8)

1 개요 & 역할

WCS가 오더와 목적지 배정을 보유한다. RCS는 AGV/로봇을 제어한다. 인덕션(투입구)에서 로봇이 트레이에 상품을 받아 WCS에 목적지를 조회하고, 그 목적지(슈트)로 이동해 트레이 수량 전량을 한 번에 틸트한다(부분 투입 없음).

  • 양방향. IF-05·IF-09·IF-10은 RCS → WCS 요청(WCS 응답). IF-08은 WCS → RCS 푸시 — 3DS 상태가 바뀔 때마다 WCS가 RCS에 알린다.
  • 도착 알림. AGV가 슈트에 도착하면 RCS가 도착 보고(IF-09)를 보낸다. 소터가 IF-08 상태에서 ready가 되면 RCS가 투입한다. (WCS가 3DS를 내부적으로 어떻게 준비하는지는 RCS와 무관.)
  • 실시간·연속. 배치(차수) 시작/종료 없음. 상품이 인덕션에 들어오는 즉시 처리.
  • 목적지 = chuteNo. 목적지는 슈트 번호로 지정한다.
  • 투입 판단은 RCS가 직접. 가부를 폴링하는 대신, RCS가 최신 목적지 상태(IF-08 푸시)를 보유하고 그 목적지가 ready일 때 투입한다 — 아니면 다음 푸시를 기다린다.

5 API 정의

IF-05 목적지 조회

제안: POST /api/v1/destination-query. 인덕션 스캔 시 1회 호출. WCS가 피스를 기록하고(추적 시작 — 결과가 NG여도 기록은 남음) 목적지·수량을 판정한다.

요청(req)응답(res)
pId, agvNo, barcode, inductionNo, qty, timeStampresult (OK / NG), chuteNo (OK일 때 포함; NG면 null)
// 요청
{ "pId": 1024, "agvNo": 7, "barcode": "8801234567890",
  "inductionNo": 2, "qty": 3, "timeStamp": "2026-06-08 14:30:00" }

// 응답 — OK
{ "result": "OK", "chuteNo": 15 }

// 응답 — NG (지금 보낼 목적지 없음)
{ "result": "NG", "chuteNo": null }

OK이면 RCS가 AGV를 chuteNo로 이동시킨다. NG이면 AGV는 대기하고 이후 다시 호출한다(사유 코드 참조).

IF-08 목적지 상태 알림 (푸시 · WCS → RCS)

제안: POST {RCS base}/api/v1/destination-status — 엔드포인트는 RCS가 제공, WCS가 호출한다. 목적지 상태가 바뀔 때마다 WCS가 푸시한다(상태 변경 시에만 — 주기 전송 아님). 목적지는 일반 슈트 또는 3D 소터 슈트이며 RCS는 동일하게 취급한다. RCS는 chuteNo별로 최신 상태를 보유하고, 자기 AGV가 그 슈트에 있을 때 ready가 되는 즉시 투입한다 — 아니면 다음 푸시를 기다린다.

요청 (WCS → RCS)응답 (RCS → WCS)
chuteNo, ready, timeStampresult (OK)
// 요청 (WCS → RCS · 상태 변경 시)
{ "chuteNo": 15, "ready": true, "timeStamp": "2026-06-22 14:30:00" }

// 응답 (RCS → WCS)
{ "result": "OK" }

ready=true = 그 목적지가 받을 수 있음(OK); ready=false = 받을 수 없음(NG). 일반 슈트는 만재·정지면 ready=false(WCS가 관리). 3D 소터 슈트의 ready=false는 운영 상태 사유만 — 분류 중·이동 중·미정렬·오프라인이다. 소터의 셀 만재·정지는 push ready를 false로 만들지 않는다(만재·정지여도 운영상태가 OK면 ready=true); 그 둘은 IF-05 투입 가부(dispatch)에서 차단된다. ready=true일 때 투입 — 아니면 대기하며 다음 푸시를 기다린다.

IF-09 도착 보고

제안: POST /api/v1/arrival-report. AGV가 목적지 슈트에 도착하면 투입 직전에 1회 호출. WCS가 도착을 기록하고 목적지를 수용 준비시킨다. 이후 RCS는 IF-08 상태 푸시에서 그 목적지가 ready가 되길 기다렸다가 투입한다.

요청(req)응답(res)
pId, chuteNo, agvNo, timeStampresult (OK)
// 요청
{ "pId": 1024, "chuteNo": 15, "agvNo": 7, "timeStamp": "2026-06-22 14:30:00" }

// 응답
{ "result": "OK" }

슈트 전용 목적지(3D 아님)면 WCS는 도착만 기록한다. 3D 소터 슈트면 WCS가 수용 준비시킨다(내부 처리 — 층 정보는 RCS와 주고받지 않음).

IF-10 투입 보고

제안: POST /api/v1/deposit-report. 틸트 후 전송. qty 전량을 한 번에 틸트한다.

요청(req)응답(res)
pId, barcode, chuteNo, agvNoresult (OK)

6 사유 코드

IF-05 사유는 WCS 내부용 — 피스 로그에 기록되며 RCS로 전송하지 않는다(RCS는 result만 수신). IF-08은 이제 가부 조회가 아니라 상태 푸시이며, 아래 표는 RCS가 그 목적지 상태를 어떻게 해석하는지를 나타낸다.

IF-05 — 목적지 조회

WCS 사유(내부)RCS 수신RCS 동작
NORMALOKAGV를 chuteNo로 이동
BUSY (분류 중·이동 중)OK그래도 chuteNo로 이동 — 지금은 분류·이동 중이지만 곧 풀림. 도착 후 소터가 IF-08 상태에서 ready가 되면 투입
FULL / PAUSED (목적지 타입별)NG 대기 / OK목적지 타입에 따라 다르다. 슈트: full/paused여도 IF-05는 OK(보내고 대기 — readiness는 IF-08 push로 별도 전달). 3D 소터: PAUSED면 NG(예외 없이 차단), 셀 기준(SorterCanAcceptBarcode)으로 못 받으면 NG(FULL); OFFLINE은 IF-05에서 보지 않는다(셀이 있으면 OFFLINE이어도 OK — 도착 후 push ready 대기). 즉 IF-05 가부는 ready(운영상태)가 아니라 paused+셀 여유로 판정한다
OVERNG 대기AGV 대기(전량이 한 목적지에 아직 안 들어감)
COMPLETED / NO_DEST / OFFLINENG 대기AGV 대기 — 보낼 목적지 없음(OFFLINE = 목적지 연결 끊김; 대체 / 보류)
각주 — 위 표의 두 OFFLINE은 다른 상황이다. FULL / PAUSED 행의 OFFLINE은 소터의 운영 상태(폴 타임아웃·소켓 끊김)로, IF-05 dispatch는 이를 보지 않으므로 셀이 있으면 OK다(도착 후 push ready 대기). COMPLETED / NO_DEST / OFFLINE 행의 OFFLINE은 목적지 자체를 확정할 수 없는 경우(연결 끊김·목적지 없음)로 NG다.

7 전체 플로우

① 목적지 조회→ ② 도착 보고 (IF-09)→ ③ 층 ready 대기 (IF-08 상태 푸시)→ ④ 투입 보고
  1. ① 목적지 조회 — 스캔 시 RCS가 IF-05 호출. OK면 AGV를 chuteNo로 이동, NG면 AGV 대기.
  2. ② 도착 보고 (IF-09) — 슈트 도착 시 RCS가 IF-09 호출. WCS가 도착을 기록하고 소터를 수용 준비시킨다.
  3. ③ ready (IF-08 푸시) — RCS가 WCS로부터 목적지 상태를 계속 수신. 그 슈트가 ready=true가 되는 즉시 투입. 아니면 다음 푸시까지 대기.
  4. ④ 투입 보고 — RCS가 목적지에서 qty 전량을 틸트하고 IF-10으로 보고.

B1 B2B 개요 & 통신

B2B 방식은 사전 등록된 테스트데이터(bizDay + batch + barcode)를 기준으로 배치 단위 투입·분류·결과를 주고받는다. 목적지(chuteNo)는 배치 데이터에 이미 지정되어 있어 WCS가 판정하지 않는다.

3DS 연동 없음. B2B에는 목적지 판정·IF-08 상태 푸시·3D 소터 핸드셰이크가 없다 — 순수 REST API 5종만으로 동작한다. (PLC 레지스터·Modbus 핸드셰이크·층 정렬 상세는 RCS 인터페이스 범위 밖이며 Part I · B2C 및 마스터 정의서 §07·§08 소관이다.)

※ 레거시 원 시스템(RCS 합의 원천 api-spec-ko.html 기준)의 주소는 192.168.0.150:5205(온프레미스·HTTP·단일 포트)였다 — 신규 배포에서는 위 배포 환경별 값으로 대체한다.

상태 두 축 (혼동 금지). 요청 본문의 status는 OK/NG(작업 결과 — 양품/불량, 정규식 ^(OK|NG)$)이고, 응답의 status는 S(성공)/F(실패, 서버 처리 성부)다. 서로 다른 축이다 — 예: status:"NG"(불량)로 온 투입도 정상 저장되면 응답은 status:"S". pId·inductionNo는 RCS가 부여하는 Integer 식별자이며, 서버는 값을 검증하지 않고 저장한다(상세는 §B2 필드표).
상충 시 본 문서가 우선한다. B2B 계약의 원천은 api-spec-ko.html이나, 본 문서는 일부 필드 길이를 의도적으로 넓혔다 — batch 1~10(원천 §1~4의 3 대신) · bizDay 8~10(YYYYMMDD·YYYY-MM-DD 모두 허용, 공통 검증·박스 §5와 일치). 원천과 어긋나면 본 문서 값을 따른다 — api-spec-ko.html의 해당 길이는 역사적 참조로만 본다.
chuteNo 정규화. 서버는 모든 엔드포인트에서 chuteNo를 3자리 zero-pad로 정규화한다(예: "3" → "003"). classification의 슈트 일치 판정("Chute mismatch")은 패딩 후 값으로 비교하므로 "1"과 "001"은 같은 슈트로 취급된다.

B2B 골든 패스 (표준 시퀀스)

RCS는 아래 순서로 호출한다. 각 단계의 목적과 실패 시 행동(특히 재시도 가부)은 다음과 같다.

① unprocessed 조회→ ② input 투입→ ③ classification 분류→ ④ box 마감 (선택)→ ⑤ results 결과
단계목적실패 시 RCS 행동
① unprocessed처리할 배치 데이터 확보 + 조회 행 "가져감" 마킹재시도하지 않는다(비멱등 — 각 호출이 행을 소비). 응답 유실 시 재조회하면 다른 행을 가져가므로 운영자 확인/재동기화. 빈 배열은 실패가 아니다.
② input투입 기록(qty 묶음)status:"F"면 전량 거부(부분 없음) — message로 원인 확인. "Not enough unprocessed rows"면 ①을 재조회해 가용량 재확인 후 재전송. 응답을 못 받은(타임아웃) 경우 이중 소비 위험이 있어 반영 여부 확인 후에만 재전송.
③ classification분류 결과 기록(qty 묶음)Chute mismatch·이미 분류됨·부족은 데이터 교정 없이는 재시도해도 동일 실패. 원인 교정 후 재전송. 타임아웃 재전송 주의는 ②와 동일.
④ box (선택)박스 단위 마감 기록동일 (bizDay,batch,boxNo) 재전송은 중복 키로 거부 — 이미 저장된 것이므로 재시도 불필요.
⑤ results전체 결과 일괄 전송(최상위 배열)미등록 barcode가 하나라도 있으면 전량 거부(부분 INSERT 없음). barcode 교정 후 전체 재전송이 안전하다.

① 미작업 차수 조회 — GET /api/v1/works/unprocessed?bizDay=

미작업 상태인 데이터 목록을 조회한다. 응답은 ApiResponse가 아니라 원시 배열이며, 데이터가 없으면 빈 배열 [] + 200을 반환한다(실패가 아님).

부수효과. 조회된 행의 ReceiveTime을 서버시각으로 갱신("가져갔다" 마킹)한다. ⚠ GET이지만 멱등이 아니다 — 응답 수신에 실패해도 단순 재시도 금지. 각 호출이 조회한 행을 소비(ReceiveTime 마킹)하므로, 재호출하면 이전 행이 아니라 다음 행 집합을 가져가 데이터가 유실될 수 있다.

B3 B2B 실패 응답 (status:"F")

실패 시 모든 엔드포인트는 {"status":"F","message":"..."}를 반환한다. 클라이언트는 HTTP 상태 코드가 아니라 항상 status 필드로 분기해야 한다. 아래 message는 서버가 반환하는 정확한 문자열이다(중괄호 {...}는 런타임 치환값).

status:"F"(서버 응답)와 요청 본문의 status:"NG"는 다르다. "F"는 서버가 호출을 거부/실패한 것이고, "NG"는 정상 수신되어 로그에 기록되는 불량 물품으로 서버는 이를 수락하고 "S"를 반환한다.

타임아웃 · 재시도 지침

  • unprocessed(GET)는 재시도하지 않는다 — 비멱등이라 각 호출이 행을 소비한다. 응답을 못 받았더라도 재조회하면 다음 행 집합을 가져가 데이터가 유실되므로, 타임아웃 시 운영자 확인·재동기화로 처리한다.
  • POST 재시도는 "서버가 처리하지 않았음이 확실할 때"만 안전하다 — 연결이 서버에 닿지 못했거나, 명확한 status:"F"를 받고 원인을 교정한 경우. 응답 없이 타임아웃난 input·classification을 그대로 재전송하면 미처리 풀을 이중 소비할 수 있으니, 재전송 전 조회(또는 results 비교)로 반영 여부를 확인한다. box 재전송은 중복 키로 거부되므로 안전하다.
  • 429는 지수 백오프로 재시도 — 분당 300건(IP당) 초과 시 발생하므로 즉시 재시도하지 말고 간격을 두고 재시도한다.
  • 500은 처리 여부가 불확실하므로 위 POST 재시도 규칙(반영 여부 확인 후)을 따른다.
