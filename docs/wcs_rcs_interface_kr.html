WCS ↔ RCS · API 인터페이스 정의서

WCS ↔ RCS 인터페이스 정의서 REST / JSON API. RCS가 목적지 조회·도착 보고·투입 보고(IF-05 / IF-09 / IF-10)를 호출하고, WCS가 목적지 상태(IF-08)를 변경 시마다 RCS로 푸시한다. 실시간·투입 단위(배치 없음). 본 문서는 WCS ↔ RCS 인터페이스를 정의한다 — 엔드포인트·인증·시간값은 예시이며 협의 가능.

1 개요 & 역할

WCS가 오더와 목적지 배정을 보유한다. RCS는 AGV/로봇을 제어한다. 인덕션(투입구)에서 로봇이 트레이에 상품을 받아 WCS에 목적지를 조회하고, 그 목적지(슈트)로 이동해 트레이 수량 전량을 한 번에 틸트한다(부분 투입 없음).

  • 양방향. IF-05·IF-09·IF-10은 RCS → WCS 요청(WCS 응답). IF-08은 WCS → RCS 푸시 — 3DS 상태가 바뀔 때마다 WCS가 RCS에 알린다.
  • 도착 알림. AGV가 슈트에 도착하면 RCS가 도착 보고(IF-09)를 보낸다. 소터가 IF-08 상태에서 ready가 되면 RCS가 투입한다. (WCS가 3DS를 내부적으로 어떻게 준비하는지는 RCS와 무관.)
  • 실시간·연속. 배치(차수) 시작/종료 없음. 상품이 인덕션에 들어오는 즉시 처리.
  • 목적지 = chuteNo. 목적지는 슈트 번호로 지정한다.
  • 투입 판단은 RCS가 직접. 가부를 폴링하는 대신, RCS가 최신 목적지 상태(IF-08 푸시)를 보유하고 그 목적지가 ready일 때 투입한다 — 아니면 다음 푸시를 기다린다.

5 API 정의

IF-05 목적지 조회

제안: POST /api/v1/destination-query. 인덕션 스캔 시 1회 호출. WCS가 피스를 기록하고(추적 시작 — 결과가 NG여도 기록은 남음) 목적지·수량을 판정한다.

요청(req)응답(res)
pId, agvNo, barcode, inductionNo, qty, timeStampresult (OK / NG), chuteNo (OK일 때 포함; NG면 null)
// 요청
{ "pId": 1024, "agvNo": 7, "barcode": "8801234567890",
  "inductionNo": 2, "qty": 3, "timeStamp": "2026-06-08 14:30:00" }

// 응답 — OK
{ "result": "OK", "chuteNo": 15 }

// 응답 — NG (지금 보낼 목적지 없음)
{ "result": "NG", "chuteNo": null }

OK이면 RCS가 AGV를 chuteNo로 이동시킨다. NG이면 AGV는 대기하고 이후 다시 호출한다(사유 코드 참조).

IF-08 목적지 상태 알림 (푸시 · WCS → RCS)

제안: POST {RCS base}/api/v1/destination-status — 엔드포인트는 RCS가 제공, WCS가 호출한다. 목적지 상태가 바뀔 때마다 WCS가 푸시한다(상태 변경 시에만 — 주기 전송 아님). 목적지는 일반 슈트 또는 3D 소터 슈트이며 RCS는 동일하게 취급한다. RCS는 chuteNo별로 최신 상태를 보유하고, 자기 AGV가 그 슈트에 있을 때 ready가 되는 즉시 투입한다 — 아니면 다음 푸시를 기다린다.

요청 (WCS → RCS)응답 (RCS → WCS)
chuteNo, ready, timeStampresult (OK)
// 요청 (WCS → RCS · 상태 변경 시)
{ "chuteNo": 15, "ready": true, "timeStamp": "2026-06-22 14:30:00" }

// 응답 (RCS → WCS)
{ "result": "OK" }

ready=true = 그 목적지가 받을 수 있음(OK); ready=false = 받을 수 없음(NG). 일반 슈트면 만재·정지(WCS가 관리), 3D 소터 슈트면 추가로 분류 중·오프라인·미정렬. WCS가 모두 플래그 하나로 접으므로 RCS는 슈트 단위 ready 하나만 보고 만재·정지 슈트엔 틸트하지 않는다. ready=true일 때 투입 — 아니면 대기하며 다음 푸시를 기다린다.

IF-09 도착 보고

제안: POST /api/v1/arrival-report. AGV가 목적지 슈트에 도착하면 투입 직전에 1회 호출. WCS가 도착을 기록하고 목적지를 수용 준비시킨다. 이후 RCS는 IF-08 상태 푸시에서 그 목적지가 ready가 되길 기다렸다가 투입한다.

요청(req)응답(res)
pId, chuteNo, agvNo, timeStampresult (OK)
// 요청
{ "pId": 1024, "chuteNo": 15, "agvNo": 7, "timeStamp": "2026-06-22 14:30:00" }

// 응답
{ "result": "OK" }

슈트 전용 목적지(3D 아님)면 WCS는 도착만 기록한다. 3D 소터 슈트면 WCS가 수용 준비시킨다(내부 처리 — 층 정보는 RCS와 주고받지 않음).

IF-10 투입 보고

제안: POST /api/v1/deposit-report. 틸트 후 전송. qty 전량을 한 번에 틸트한다.

요청(req)응답(res)
pId, barcode, chuteNo, agvNoresult (OK)
// 요청
{ "pId": 1024, "barcode": "8801234567890", "chuteNo": 15, "agvNo": 7 }

// 응답
{ "result": "OK" }

6 사유 코드

IF-05 사유는 WCS 내부용 — 피스 로그에 기록되며 RCS로 전송하지 않는다(RCS는 result만 수신). IF-08은 이제 가부 조회가 아니라 상태 푸시이며, 아래 표는 RCS가 그 목적지 상태를 어떻게 해석하는지를 나타낸다.

IF-05 — 목적지 조회

WCS 사유(내부)RCS 수신RCS 동작
NORMALOKAGV를 chuteNo로 이동
BUSY (분류 중·이동 중)OK그래도 chuteNo로 이동 — 지금은 분류·이동 중이지만 곧 풀림. 도착 후 소터가 IF-08 상태에서 ready가 되면 투입
FULL / PAUSEDNG 대기AGV 대기 — 그 목적지가 받을 수 없음(장기 차단). 가부 조회(IF-08)가 없어졌으므로 WCS가 만재·정지 목적지는 배정하지 않는다
OVERNG 대기AGV 대기(전량이 한 목적지에 아직 안 들어감)
COMPLETED / NO_DEST / OFFLINENG 대기AGV 대기 — 보낼 목적지 없음(OFFLINE = 목적지 연결 끊김; 대체 / 보류)

IF-08 — 목적지 상태 알림 (RCS의 해석)

푸시된 상태RCS 동작
ready=true (OK)투입 틸트 진행
ready=false (NG)대기 그 목적지가 지금 받을 수 없음(만재·정지; 소터면 분류 중·오프라인도) — 이후 푸시에서 ready로 바뀌면 투입
full / paused / online=false대기 소터가 받을 수 없음 — 이후 푸시로 해소될 때까지 보류

7 전체 플로우

① 목적지 조회→ ② 도착 보고 (IF-09)→ ③ 층 ready 대기 (IF-08 상태 푸시)→ ④ 투입 보고
  1. ① 목적지 조회 — 스캔 시 RCS가 IF-05 호출. OK면 AGV를 chuteNo로 이동, NG면 AGV 대기.
  2. ② 도착 보고 (IF-09) — 슈트 도착 시 RCS가 IF-09 호출. WCS가 도착을 기록하고 소터를 수용 준비시킨다.
  3. ③ ready (IF-08 푸시) — RCS가 WCS로부터 목적지 상태를 계속 수신. 그 슈트가 ready=true가 되는 즉시 투입. 아니면 다음 푸시까지 대기.
  4. ④ 투입 보고 — RCS가 목적지에서 qty 전량을 틸트하고 IF-10으로 보고.
