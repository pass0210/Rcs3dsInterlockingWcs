◎ 2가지 운영 방식 (B2C 실시간 / B2B 배치)

WCS는 두 가지 운영 방식으로 RCS와 연동한다. 엔드포인트 집합이 완전히 분리되어 있으므로 담당하는 방식의 파트만 읽으면 된다. 본 통합 정의서의 §00~§10(3DS 포함)은 전부 B2C이며, B2B는 문서 끝의 Part II에서 별도로 다룬다.

B2C / B2B는 이 문서에서 연동 방식(통신 계약)을 가리키는 라벨이다. 어느 쪽을 읽을지 — 라이브 3D 소터에 실시간으로 틸트하면 B2C(Part I · §00~§10), 사전 등록된 배치 데이터를 소비하면 B2B(Part II)를 읽는다. B2B도 정식 운영 경로다 — "배치 테스트데이터 방식"이라는 이름이지만 테스트 전용이 아니라 실제 운영에 사용된다.

00 개요 & 시스템 구성

WCS(자사, 오더 보유)가 RCS(AGV·로봇)와 3D Sorter(VEICHI PLC)를 연동한다. 로봇이 인덕션에서 트레이를 받아, 목적지(슈트 또는 3D 셀)에 상품 전량을 한 번에 틸트한다.

  • 실시간 연속 운영 — 배치(차수) 시작/종료 개념 없음. 인덕션부터 바로 처리(작업 데이터 수신·시작·종료·결과 전송 IF 제외).
  • 목적지 = chuteNo — 슈트/3D를 하나의 번호로 식별(메시지에 destType 없음). 투입 보고도 슈트/3D 구분 없이 동일.
  • 한 번에 전량 틸트 — 한 트레이에 같은 상품 여러 개(qty)를 싣고, 한 목적지에 전량을 한 번에. 부분 투입 불가.

05 목적지 조회 (IF-05) 사유

WCS가 목적지(chuteNo)와 수량을 판정한다. BUSY(분류 중·이동 중)는 일시적이라 그 목적지로 그대로 배정(도착 후 IF-08 상태에서 ready가 되면 투입). FULL·PAUSED는 목적지 타입별로 갈린다 — 슈트는 곧 비워지니 IF-05는 OK(보내고 대기, readiness는 IF-08 푸시로 별도 전달), 3D 소터는 PAUSED·셀 만재면 NG(가부 조회 IF-08 폐지로 도착 후 거를 수 없어 IF-05에서 막는다).

06 목적지 상태 알림 (IF-08) — WCS → RCS 푸시

기존 투입 가부 조회(RCS 폴링)를 폐지하고, WCS가 목적지 상태를 변경 시마다 RCS로 푸시한다(PUT /api/UpdateChuteState). 일반 슈트와 3D 소터 슈트를 동일 인터페이스로 알린다. 상태가 바뀐 목적지의 층으로 라우팅 — 층별 수신 호스트(1층 192.168.0.151:3000·2층 192.168.0.152:3000)로 next_state(3=받을 수 있음/2=받을 수 없음)를 보낸다. 층은 페이로드가 아니라 수신 호스트로 전달된다. 수용 산출: 일반 슈트 = !full && !paused이면 자기 층 호스트에 3 · 소터 슈트(정렬로 두 층 겸용) = online·!full·!paused·Ready=1·CurFloor==F이면 F층 호스트에 3, 다른 층 호스트엔 사실상 2(그 층엔 지금 서비스 안 함). 셀 만재는 push에 반영 안 함(IF-05 dispatch에서 차단). 이로써 RCS가 만재·정지·미정렬 슈트엔 틸트하지 않는다. 기동 시엔 전 목적지의 현재 상태를 1회 부트스트랩 푸시한다(DestinationStatusPusher.StartAsync) — 소터는 두 층 호스트 모두에 발신(현재 CurFloor 호스트=3 수용 시 / 다른 층 호스트=2; CurFloor에서도 미수용이면 둘 다 2), 고정 슈트는 자기 층 호스트 1곳. 이후로는 전이 시에만 푸시한다(부트스트랩·전이 동일 규칙).

3DS 정렬은 IF-05 시점(인덕션 파생 층 F) — WCS가 IF-05 요청 inductionNo로 층 F를 파생하고, 소터 목적지면 도착 전에 3DS를 F층으로 정렬한다(TgtFloor=F D6, §07, ==0일 때만 씀). 정렬돼 F층 수용 가능이 되면 IF-08로 F층 호스트에 3을 푸시하고 RCS가 투입. 도착 보고(IF-09)(pId·chuteNo·agvNo)는 도착 기록만 하며 층 필드가 없다(과거 "IF-09가 2층 고정 정렬을 트리거"는 폐지 — 2026-07-21). 층은 페이로드가 아니라 IF-08 수신 호스트로 전달된다.

핸드셰이크 규칙

  1. 쓰기 전 해당 Flag=0 확인 — 아직 안 읽힌 값을 덮어쓰지 않도록(C_Flag / R_Flag 각각).
  2. C 영역: WCS가 C_Flag=0일 때 C값 쓰고 C_Flag=1 → PLC가 C값 읽고 C_CellNo·C_Seq·C_Flag=0 클리어 후 적재.
  3. R 영역: PLC가 R_Flag=0일 때 R값 쓰고 R_Flag=1 → WCS가 R값 읽고 R_Seq==C_Seq 대사 후 R_CellNo·R_Seq·R_Flag=0 클리어.
  4. 층 폐루프(인덕션 파생 층 F · 소터별 FIFO 큐): IF-05는 소터 피스를 소터별 pending-floor 큐(FIFO · IF-05 순서)에 enqueue만 한다. WCS는 TgtFloor==0을 관측하고 (CurFloor≠F 또는 분류 중)일 때 큐 머리 피스의 층 F를 TgtFloor에 쓴다 → F층 아니면 이동, 분류 중이면 분류 후 F층 복귀 → 도착 시 PLC가 CurFloor=F 기입(TgtFloor 유지) → WCS가 CurFloor==F 확인되면 그 층 수용 산출. TgtFloor는 분류 시작(BUSY 진입) 시 PLC가 0으로 클리어 → WCS가 그 TgtFloor==0을 관측해 큐의 다음 층을 즉시 기입하고 소터가 그 층으로 복귀("타겟층을 순서대로" · 층은 큐가 공급하고 쓰기는 게이트로 트리거 — sort-completion 이벤트 아님 · 머리 pop 시점 세부는 코드 스프린트 확정). TgtFloor≠0이면 덮어쓰지 않아 핑퐁 차단. ※ 층 F=인덕션 파생(2026-06-22 "운영 2층 고정" 폐지 — 2026-07-21).
“쓰는 쪽은 Flag=0 확인 후 쓰고 1, 읽는 쪽은 읽고 0.” C는 WCS가 쓰고 PLC가 클리어, R은 PLC가 쓰고 WCS가 클리어 — 대칭. 틸트 낙하 대기는 PLC가 N초 지연으로 처리(WCS 측 지연 없음). 모든 레지스터는 Holding Register(읽기 FC03 · 쓰기 FC06/16)이고 C_Flag·R_Flag·Ready는 워드 D4의 비트0·1·2다 — 한 비트만 바꿀 땐 D4 read-modify-write(상대 비트 보존). 주소는 3DS 제공 맵(D0~D4) + 층 신설(D5·D6).

08 핵심 플로우

① 인덕션·목적지 조회(IF-05) → 층 F 파생·F층 정렬→ ② 3DS 상태 푸시(IF-08 · F층 호스트) → RCS 투입 판단→ ③ 도착 보고(IF-09 · 층 없음)→ ④ 투입(슈트/3D 공통)
  1. ① 인덕션·목적지 조회 — 스캔(qty) → (판독 실패 시 NO_READ·재스캔/리젝트) → IF-05(라인 투입 기록 + 목적지·수량 판정). 이 시점에 WCS가 inductionNo→층 F를 파생하고 소터면 그 피스를 소터별 FIFO 큐에 넣는다 — TgtFloor에는 큐 머리 층을 게이트 허용(==0) 시 기입(순서대로, §07). → OK·chuteNo(NORMAL·BUSY) / NG·대기(FULL·PAUSED·OVER·COMPLETED·NO_DEST·OFFLINE).
  2. ② 목적지 상태 알림 — IF-08: WCS가 목적지(슈트/소터) 상태 변경 시마다 RCS로 푸시(next_state 3/2 · 층별 호스트). 소터가 F층 정렬·수용 가능이면 F층 호스트에 3. RCS는 그 목적지가 3(열림)일 때 투입, 아니면 대기 — 미수용 AGV는 목적지 앞이 아니라 파킹존에서 대기하다 열림(3) 수신 시 목적지로 이동.
  3. ③ 도착 보고 — IF-09: (파킹존→)목적지 도착 시 → WCS는 도착만 기록(층 필드 없음 · 정렬은 ①에서 이미 수행). 미개방 목적지에선 ②의 열림 푸시가 이 도착보다 먼저다(이미 열림이면 직행).
  4. ④ 투입 — IF-10 투입 보고 → IF-11 셀 지정(C_Flag=0 확인 후 1) → PLC가 C 읽고 초기화 → 적재(R_Flag=0 확인 후 1) → WCS R_Flag 폴링 → R 읽고 초기화. 이후 분류 후 복귀: 분류 시작 시 PLC가 TgtFloor=0 클리어 → WCS가 TgtFloor==0 관측 시 큐 다음 층 기입 → 소터 그 층으로 이동·도착 시 CurFloor 기입.

10 확정 사항 (PLC 협의 완료)

  • PLC가 주는 상태 = 수용 가능 여부(Ready=D4.2) — Ready=0은 분류 중 또는 이동 중(둘 다 받을 수 없음). FULL(만재)·PAUSED(일시정지)·OFFLINE은 WCS가 판단한다(만재=예약/수량, 일시정지=운영 상태, OFFLINE=폴 타임아웃). BUSY/FULL 구분용 별도 PLC 비트는 두지 않는다.
  • TgtFloor 쓰기 = 0일 때 + (CurFloor≠F 또는 분류 중) · 인덕션 파생 층 F — TgtFloor==0이고 F층이 아니거나 분류 중(BUSY)이면 TgtFloor=F를 써서 F층으로 이동/복귀시킨다(층 F=IF-05 inductionNo 파생 · 2026-06-22 "운영 2층 고정" 폐지 — 2026-07-21). 쓰기 트리거는 IF-05 목적지 조회 시점. 진행 중(≠0)엔 덮어쓰지 않아 핑퐁 차단. 도착 시엔 CurFloor만 기입(TgtFloor 유지), 분류 시작 시 TgtFloor=0 클리어. FULL/PAUSED/OFFLINE은 쓰지 않고 대기.
  • 플래그 위치 확정 — C_Flag=D4.0 · R_Flag=D4.1 · Ready=D4.2 (3DS 맵). 같은 워드(D4)라 한 비트만 바꿀 땐 read-modify-write.
Part II · B2B
배치 테스트데이터 방식
사전 등록된 테스트데이터(bizDay + batch + barcode) 기반의 배치 투입/분류/결과 전송. 5개 REST 엔드포인트로만 구성되며, 위 §07 레지스터·§08 핸드셰이크·IF-06/11/12·층 정렬과 전혀 무관하다.

B1 개요 & 역할

B2B 방식은 사전 등록된 테스트데이터(bizDay + batch + barcode)를 기준으로 배치 단위 투입·분류·결과를 주고받는다. 목적지(chuteNo)는 배치 데이터에 이미 지정되어 있어 WCS가 판정하지 않는다.

  • 배치 기반. 처리 단위는 bizDay/batch로 묶인 사전 등록 데이터다 — 실시간 피스 스트림(B2C)이 아니다.
  • 목적지 판정 없음. chuteNo가 배치에 이미 들어 있어 WCS가 목적지를 계산하지 않는다.
  • 단방향 호출. 5종 엔드포인트 모두 RCS → WCS다(unprocessed는 GET, 나머지는 POST). WCS → RCS 상태 푸시(IF-08)가 없다.
  • 실패 분기는 status로. 클라이언트는 HTTP 상태 코드가 아니라 응답 status(S/F) 필드로 처리 성부를 판단한다.
B2B는 3DS Modbus/핸드셰이크와 무관 — 본 파트는 REST API만 다룬다. B2B는 §07 PLC 레지스터(C/R/Ready·D0~D6)·§08 핸드셰이크·IF-06(상태 조회)·IF-11(셀 지정)·IF-12(적재 완료)·층 정렬(인덕션 파생 층)·IF-08 상태 푸시·목적지 판정의 대상이 전혀 아니다. 이 섹션들은 모두 Part I · B2C(3D 소터) 전용이며, B2B는 순수 REST API 5종만으로 동작한다.

chuteNo 정규화. 서버는 모든 엔드포인트에서 chuteNo를 3자리 zero-pad로 정규화한다(예: "3" → "003"). classification의 슈트 일치 판정("Chute mismatch")은 패딩 후 값으로 비교하므로 "1"과 "001"은 같은 슈트로 취급된다.
상태 두 축 (혼동 금지). 요청 본문의 status는 OK/NG(작업 결과 — 양품/불량, 정규식 ^(OK|NG)$)이고, 응답의 status는 S(성공)/F(실패, 서버 처리 성부)다. 서로 다른 축이다 — 예: status:"NG"(불량)로 온 투입도 정상 저장되면 응답은 status:"S". pId·inductionNo는 RCS가 부여하는 Integer 식별자이며, 서버는 값을 검증하지 않고 저장한다(상세는 위 공통 필드표).
상충 시 본 문서가 우선한다. B2B 계약의 원천은 api-spec-ko.html이나, 본 문서는 일부 필드 길이를 의도적으로 넓혔다 — batch 1~10(원천 §1~4의 3 대신) · bizDay 8~10(YYYYMMDD·YYYY-MM-DD 모두 허용, 공통 검증·박스 §5와 일치). 원천과 어긋나면 본 문서 값을 따른다 — api-spec-ko.html의 해당 길이는 역사적 참조로만 본다.

B5 API 정의

각 엔드포인트 표는 고유·변형 필드만 싣는다 — 공통 필드(bizDay·batch·chuteNo·barcode·qty·status·reason·pId·inductionNo)의 타입·길이·설명은 B3를 참조한다.

① 미작업 차수 조회 — GET /api/v1/works/unprocessed?bizDay=

미작업 상태인 데이터 목록을 조회한다. 응답은 ApiResponse가 아니라 원시 배열이며, 데이터가 없으면 빈 배열 [] + 200을 반환한다(실패가 아님).

부수효과. 조회된 행의 ReceiveTime을 서버시각으로 갱신("가져갔다" 마킹)한다. ⚠ GET이지만 멱등이 아니다 — 응답 수신에 실패해도 단순 재시도 금지. 각 호출이 조회한 행을 소비(ReceiveTime 마킹)하므로, 재호출하면 이전 행이 아니라 다음 행 집합을 가져가 데이터가 유실될 수 있다.
※ 미처리가 0건이면 빈 배열 []을 반환한다(실패 아님).

요청 — bizDay(쿼리 파라미터, 공통 B3) 단독. 고유 필드 없음.

B6 실패 응답 & 사유 (status:"F")

실패 시 모든 엔드포인트는 {"status":"F","message":"..."}를 반환한다. 클라이언트는 HTTP 상태 코드가 아니라 항상 status 필드로 분기해야 한다. 아래 message는 서버가 반환하는 정확한 문자열이다(중괄호 {...}는 런타임 치환값).

status:"F"(서버 응답)와 요청 본문의 status:"NG"는 다르다. "F"는 서버가 호출을 거부/실패한 것이고, "NG"는 정상 수신되어 로그에 기록되는 불량 물품으로 서버는 이를 수락하고 "S"를 반환한다.

B7 전체 플로우 (골든 패스)

RCS는 아래 순서로 호출한다. 각 단계의 목적과 실패 시 행동(특히 재시도 가부)은 다음과 같다.

① unprocessed 조회→ ② input 투입→ ③ classification 분류→ ④ box 마감 (선택)→ ⑤ results 결과
단계목적실패 시 RCS 행동
① unprocessed처리할 배치 데이터 확보 + 조회 행 "가져감" 마킹재시도하지 않는다(비멱등 — 각 호출이 행을 소비). 응답 유실 시 재조회하면 다른 행을 가져가므로 운영자 확인/재동기화. 빈 배열은 실패가 아니다.
② input투입 기록(qty 묶음)status:"F"면 전량 거부(부분 없음) — message로 원인 확인. "Not enough unprocessed rows"면 ①을 재조회해 가용량 재확인 후 재전송. 응답을 못 받은(타임아웃) 경우 이중 소비 위험이 있어 반영 여부 확인 후에만 재전송.
③ classification분류 결과 기록(qty 묶음)Chute mismatch·이미 분류됨·부족은 데이터 교정 없이는 재시도해도 동일 실패. 원인 교정 후 재전송. 타임아웃 재전송 주의는 ②와 동일.
④ box (선택)박스 단위 마감 기록동일 (bizDay,batch,boxNo) 재전송은 중복 키로 거부 — 이미 저장된 것이므로 재시도 불필요.
⑤ results전체 결과 일괄 전송(최상위 배열)미등록 barcode가 하나라도 있으면 전량 거부(부분 INSERT 없음). barcode 교정 후 전체 재전송이 안전하다.

B8 타이밍 & 재시도

항목값비고
레이트리밋IP당 분당 300건초과 시 429 — 아래 재시도 규칙 참조
  • unprocessed(GET)는 재시도하지 않는다 — 비멱등이라 각 호출이 행을 소비한다. 응답을 못 받았더라도 재조회하면 다음 행 집합을 가져가 데이터가 유실되므로, 타임아웃 시 운영자 확인·재동기화로 처리한다.
  • POST 재시도는 "서버가 처리하지 않았음이 확실할 때"만 안전하다 — 연결이 서버에 닿지 못했거나, 명확한 status:"F"를 받고 원인을 교정한 경우. 응답 없이 타임아웃난 input·classification을 그대로 재전송하면 미처리 풀을 이중 소비할 수 있으니, 재전송 전 조회(또는 results 비교)로 반영 여부를 확인한다. box 재전송은 중복 키로 거부되므로 안전하다.
  • 429는 지수 백오프로 재시도 — 분당 300건(IP당) 초과 시 발생하므로 즉시 재시도하지 말고 간격을 두고 재시도한다.
  • 500은 처리 여부가 불확실하므로 위 POST 재시도 규칙(반영 여부 확인 후)을 따른다.
