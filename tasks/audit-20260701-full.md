### A-1. [MAJOR/concurrency] HandshakeOrchestrator R단계가 R_Flag를 '레벨'로 읽어 직전 핸드셰이크의 stale R_Flag=1 스냅샷을 새 건의 응답으로 오인 — 허위 RSEQ_MISMATCH
- **위치**: src/Wcs.PlcGateway/HandshakeOrchestrator.cs:184
- **근거**: WaitRFlagAndProcessAsync: `await Task.Delay(_opt.RFlagPollMs, ct); var snap = _gw.Latest; ... if (snap.RFlag) { int rCellNo = snap.RCellNo; int rSeq = snap.RSeq; ... if (rSeq != cSeq) { ... HS_RSEQ_MISMATCH ... } }` (172-210). 직전 건 성공 경로는 `await _gw.EnqueueAsync(new PlcWrite.ClearR(), ct)`(214) 후 즉시 반환 — ClearR 처리·폴 재독을 기다리지 않음. `_gw.Latest`는 PlcPollingService가 PollIntervalMs(appsettings 150ms)마다 갱신하는 캐시이고, R폴 첫 체크는 100ms(RFlagPollMs) 후라 100<150 창이 존재. 에지 감지용 `RFlagRaised` 채널은 존재하나 미사용(170-171 "여기서는 폴링 방식").
- **영향**: 핸드셰이크 N이 COMPLETED로 끝난 직후(스냅샷 캐시가 아직 RFlag=1·RSeq=N인 최대 ~PollIntervalMs 창) 같은 소터에 핸드셰이크 N+1이 시작되면, N+1의 첫 R체크가 직전 건의 stale RFlag=1/RSeq=N을 읽어 rSeq(N)≠cSeq(N+1) → 허위 R_SEQ_MISMATCH 알람 + sorter_command MISMATCH 행 + 불필요한 ClearR 재투입. PLC는 아무 잘못이 없는데 '유실·중복 의심' ERROR가 남아 현장 운영자를 오도한다. 트리거는 RCS 복구 후 밀린 deposit-report 연속 드레인 등 같은 소터 연속 핸드셰이크 간격 <~150ms. 알려진 F1b(동시 IF-10 직렬화 부재)·IT4b flake(RSeqMismatch)와 증상은 같으나, 이 건은 '동시'가 아니라 '순차 연속'에서도 레벨-읽기 때문에 발생하는 별개 근본원인이며 미등재. IT4b 저빈도 flake의 실제 기전일 가능성이 높다.
- **권고**: C 투입 후 R 대기를 '레벨'이 아니라 '전이'로 무장(arming): CellAssign 투입 후 (a) 먼저 RFlag==0 스냅샷을 1회 관찰한 뒤에만 RFlag==1을 수용하거나, (b) 스냅샷 At이 CellAssign 처리 시각 이후인 것만 수용하거나, (c) 이미 있는 RFlagRaised(0→1 에지) 채널을 소비. F1b per-소터 직렬화와 별개로 필요(직렬 dispatch에서도 발생).
- **검증 노트(적대적 검증자)**: 코드 사실 전부 검증됨: (1) HandshakeOrchestrator.cs:172-188이 Task.Delay(RFlagPollMs=100ms) 후 _gw.Latest를 레벨로 읽어 RFlag=1을 무조건 수용 — RFlag==0 선관찰(arming)·스냅샷 At 시각 검사 없음, RFlagRaised 에지 채널(PlcGateway.cs:143)은 미사용(170-171 주석). (2) 성공 경로(214-219)는 ClearR을 enqueue만 하고 즉시 반환하며 EnqueueAsync 계약 자체가 완료 비대기(PlcGateway.cs:18-19). (3) PollIntervalMs=150 > RFlagPollMs=100 (appsettings.json:50,58)이라 직전 건의 RFlag=1/RSeq=N 스냅샷이 N+1의 첫 R체크에 잡히는 실창 존재(back-to-back 시 대략 절반 확률, RTU에선 ClearR 3트랜잭션이 _clientLock으로 폴과 직렬화돼 창 확대). (4) 우회 방어 없음 — Sim이 C 수신 즉시 C_Flag 클리어(SimServer.cs:169-175)라 N+1의 WaitCFlagZeroAsync(첫 체크 무지연, 131-141)와 쓰기 컨슈머 CFlag 가드(PlcGateway.cs:410-411) 모두 같은 stale 스냅샷으로 즉시 통과. 발견 미기재 악화 요인: 허위 MISMATCH 후 진짜 R(N+1)은 대기자 없이 잔류 → N+2가 이를 읽어 또 MISMATCH → 재시도 정책 부재(SPEC §7:109) 하에 off-by-one 연쇄가 자가 지속(1회 발화가 이후 전 건 ERROR 영속화로 확대). 등재 여부: todo.md:34(F1b)는 '동시' IF-10만 다루며 오히려 "순차 dispatch면 전부 COMPLETED"라고 단언(E2E 타이밍 20/30ms+HTTP/DB 간격에서만 입증된 명제) — 본 건은 per-소터 락(F1b 해법)으로도 해소 안 되는 별개 근본원인이고, todo.md:35(IT4b flake)는 CPU/소켓 경합으로만 귀속·이 기전 미기록, SPEC §7에도 없음 → already_tracked=false 정당. 심각도: 현 현장 단계(Postman 수동, 수 초 간격)에선 발화 불가하나, 실 RCS 투입 시 같은 소터 <~150ms 연속 건에서 발화하고 연쇄 잠금으로 sorter_command 전 건 MISMATCH ERROR + 유지보수자가 todo의 '순차 안전' 단언에 오도됨 — major 유지.
